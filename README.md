校园失物招领系统
=======================

一、项目背景与建设意义
-----------

在高校校园中，学生和教职工数量庞大，人员流动频繁，物品遗失与拾取情况普遍存在。传统的失物招领方式多依赖公告栏、微信群或人工登记，存在**信息分散、更新不及时、查询效率低、责任不清晰、信息真实性难以核验**等突出问题，导致失物找回率低、招领信息流转不畅。

为解决上述痛点，提高校园失物招领管理的规范性与效率，特建设**统一的校园失物招领系统**。系统实现失物与招领信息的集中发布、审核、查询、认领和统计管理，打通信息壁垒，明确责任主体，为师生提供便捷、高效、可信的失物招领服务。

本系统以 **PC Web 网站** 为核心载体，面向学生、教师、失物招领管理员和系统管理员四类用户（原文档将学生 / 老师合并为一类，此处明确用户细分），后续可在不修改核心业务逻辑的前提下，无缝扩展为 **微信小程序**、**APP** 等多终端形态。
二、系统建设目标

--------

1. **信息集中化**：建立统一的校园失物招领信息平台，规范信息发布、审核、流转全流程，消除信息孤岛。

2. **查询精准化**：提供多维度、多条件组合查询能力，支持模糊搜索与精准筛选，提高失物与招领信息的匹配效率。

3. **流程规范化**：引入审核机制、状态流转机制、操作日志机制，保障信息真实性、流程可追溯性。

4. **权限精细化**：实现角色分级管理，明确学生 / 老师、失物招领管理员、系统管理员的操作权限边界，遵循最小权限原则。

5. **管理智能化**：为管理员提供数据统计、分析、导出能力，支持决策优化；自动化处理过期信息，减轻人工负担。

6. **架构可扩展**：系统设计遵循高内聚低耦合原则，具备良好的扩展性、兼容性和安全性，符合软件工程规范。

三、系统用户角色与权限分析
-------------

### 3.1 用户角色划分

系统采用 “单用户表 + 角色标识” 设计，所有用户统一存储，通过 role 字段区分权限，具体角色划分如下：

| 角色名称    | 身份说明             | 核心职责                             |
| ------- | ---------------- | -------------------------------- |
| 学生      | 在校学生（账号为学号）      | 发布失物 / 招领信息、查询信息、提交认领申请、管理个人发布记录 |
| 教师      | 在校教职工（账号为工号）     | 同学生权限，无额外限制                      |
| 失物招领管理员 | 负责失物招领日常管理的工作人员  | 审核发布信息、维护物品状态、更新物品信息、统计查询历史数据    |
| 系统管理员   | 负责系统配置与权限管理的技术人员 | 账号管理、系统参数配置、公告管理、数据备份与维护、全局统计查看  |

> 注：学生与教师统一归类为 “普通用户”，共享核心功能；权限差异仅体现在账号标识（学号 / 工号），无功能区别。

### 3.2 权限设计原则

1. **权限最小化**：不同角色仅能访问其工作必需的功能模块，禁止越权操作（如普通用户无法查看其他用户联系方式）。

2. **后端强校验**：所有敏感操作（如审核、状态修改、账号管理）均由后端进行权限校验，前端仅做界面隐藏，不作为权限控制依据。

3. **操作可追溯**：关键操作（如审核驳回、状态变更、账号禁用）均记录操作人、操作时间、操作原因，存入操作日志表，支持审计。

4. **账号状态可控**：所有账号均包含 “正常”“禁用” 状态，系统管理员可禁用失物招领管理员账号，失物招领管理员无权禁用普通用户账号。

四、系统功能需求分析
----------

### 4.1 普通用户（学生 / 老师）功能模块

#### 4.1.1 用户登录

* **登录凭证**：使用学号（学生）/ 工号（教师）作为用户名，初始密码为身份证后六位。

* **强制修改密码**：首次登录时，系统强制跳转至密码修改页面，新密码需满足 “长度≥8 位、包含字母 + 数字” 的复杂度要求，修改成功后方可进入系统。

* **密码找回**：支持通过绑定的手机号（由学校统一录入）接收验证码找回密码，或联系系统管理员重置密码。

* **登录态管理**：登录后系统生成会话令牌（Token），有效期为 2 小时，超时自动退出；支持手动退出登录。

#### 4.1.2 系统公告查看

* 登录后自动弹出公告弹窗，展示当前生效的系统公告（如 “失物招领中心办公时间调整通知”），用户需点击 “确认” 后才可进入主界面。

* 主界面右上角提供 “公告列表” 入口，可查看历史公告（按发布时间倒序排列）。

#### 4.1.3 失物 / 招领信息查询

* **查询维度**：支持按 “物品类型”“丢失 / 拾取地点”“时间范围”“物品状态”“关键词” 进行多条件组合查询。

* 物品类型：由系统管理员预设（如电子设备、证件、文具、衣物等），支持多级分类（如电子设备→手机、电子设备→电脑）。

* 地点：支持选择校园内具体地点（如教学楼 A 栋、图书馆 3 楼、食堂 2 楼），由系统管理员维护地点表。

* 时间范围：支持选择 “近 1 天”“近 3 天”“近 7 天”“近 30 天” 或自定义时间区间。

* 物品状态：失物信息支持 “待审核”“已通过”“已匹配”“已认领”“已取消”；招领信息支持 “待审核”“已通过”“已认领”“已归档”“已驳回”。

* **查询结果**：分页显示查询结果，每页默认 10 条，支持切换页码；结果列表展示核心信息（物品名称、类型、地点、时间、状态、发布人类型）。

* **详情查看**：点击列表项进入详情页，展示完整信息（物品描述、特征、照片、发布时间、联系人信息 - 仅失主 / 拾主可见）。

#### 4.1.4 发布失物信息

* **必填字段**：物品名称、物品类型、丢失地点、丢失时间（精确到小时）、物品特征（≥10 字，需描述关键特征如颜色、品牌、型号、标记等）、联系人姓名、联系电话（需验证手机号格式）。

* **可选字段**：悬赏金额（非负整数）、悬赏说明、物品照片（最多 3 张，支持 JPG/PNG 格式，单张大小≤5MB）。

* **提交规则**：表单填写完整后提交，提交后状态为 “待审核”，等待失物招领管理员审核。

* **重复校验**：系统自动校验近 7 天内是否有相同物品类型、丢失地点、核心特征的失物信息，若存在则提示用户 “已有相似失物信息，是否查看？”。

#### 4.1.5 发布招领信息

* **必填字段**：物品名称、物品类型、拾取地点、拾取时间（精确到小时）、物品特征（≥10 字）、联系人姓名、联系电话（需验证手机号格式）、物品照片（至少 1 张，最多 3 张，要求清晰展示物品全貌及关键特征，支持 JPG/PNG 格式，单张大小≤5MB）。

* **提交规则**：表单填写完整且照片上传符合要求后提交，状态为 “待审核”。

* **照片校验**：系统自动检测照片清晰度，若清晰度不达标则提示用户 “请上传清晰的物品照片，便于失主确认”。

#### 4.1.6 我的发布管理

* **列表展示**：按发布时间倒序展示本人发布的所有失物 / 招领记录，支持按 “失物 / 招领”“状态” 筛选。

* **状态说明**：

* 待审核：信息已提交，等待管理员审核。

* 已通过：信息审核通过，可在前台展示供查询。

* 已匹配：失物信息与招领信息初步匹配（管理员手动匹配）。

* 已认领：物品已成功认领，状态锁定。

* 已驳回：信息未通过审核，展示驳回原因。

* 已取消：用户主动取消发布（仅 “已通过” 且未认领状态可取消）。

* 已归档：招领信息超过认领时效，由管理员归档。

* **操作权限**：

* 待审核：支持修改、删除信息。

* 已通过（未认领 / 未匹配）：支持补充信息（如新增照片、完善特征）、取消发布。

* 已匹配 / 已认领 / 已驳回 / 已归档：仅支持查看，不可修改或删除。

#### 4.1.7 认领与沟通

* **认领申请**：普通用户查看招领信息详情后，若确认是本人失物，可点击 “提交认领申请”，填写 “额外特征证明”（≥5 字，如物品内的个人信息、隐藏标记等），提交后等待管理员审核。

* **进度查看**：在 “我的认领” 中查看申请记录，状态包括 “待审核”“审核通过”“审核驳回”“已认领”。

* **有限沟通**：

* 认领申请审核通过后，系统向失主（认领人）展示拾主的联系电话（或由管理员作为中介转发联系方式），便于线下对接。

* 支持通过系统内置留言功能向管理员发送咨询（如 “物品存放地点在哪里？”），管理员回复后用户将收到站内通知。

#### 4.1.8 个人中心

* 支持查看个人账号信息（学号 / 工号、姓名、联系方式），修改密码（需输入原密码验证）。

* 查看站内通知（如认领申请审核结果、管理员留言），未读通知标红提示。

#### 4.1.9 退出登录

* 点击 “退出登录” 按钮，销毁当前会话令牌，返回登录页面。

### 4.2 失物招领管理员功能模块

#### 4.2.1 管理员登录

* **登录凭证**：使用系统管理员分配的工号（专属管理员账号）和初始密码登录，首次登录需强制修改密码（密码复杂度要求同普通用户）。

* **登录态管理**：会话有效期为 4 小时，超时自动退出；支持手动退出。

#### 4.2.2 发布信息审核

* **审核列表**：默认展示 “待审核” 的失物 / 招领信息列表，支持按 “失物 / 招领”“发布时间” 筛选，分页显示。

* **审核内容**：

* 真实性：核实信息是否存在虚假（如虚构失物、重复发布）。

* 完整性：检查必填字段是否填写完整，特征描述是否清晰。

* 照片合规性：招领信息照片是否清晰、是否与物品匹配；失物信息照片是否合规（无违规内容）。

* **审核操作**：

* 审核通过：点击 “通过”，信息状态更新为 “已通过”，同步至前台查询列表。

* 驳回：点击 “驳回”，必须填写驳回原因（≥5 字，如 “物品特征描述不清晰，请补充关键信息”），信息状态更新为 “已驳回”，用户将收到站内通知。

* **历史记录**：支持查看 “已审核” 记录（按审核时间倒序排列），可筛选 “通过”“驳回” 状态。

#### 4.2.3 物品状态管理

* **状态更新**：

* 已通过→已匹配：管理员发现失物与招领信息匹配时，手动关联双方信息，更新状态为 “已匹配”，并通知双方用户。

* 已匹配→已认领：双方完成线下认领后，管理员确认无误，更新状态为 “已认领”。

* 已通过→已归档：招领信息发布满 30 天仍无人认领，管理员标记为 “已归档”，并记录物品处理方式（如 “移交学校后勤处”“捐赠公益”）。

* 已通过→无效：发现信息虚假、重复或违规时，标记为 “无效” 并删除，记录操作原因。

* **批量处理**：支持对多条信息批量更新状态（如批量归档超过 30 天的招领信息）。

#### 4.2.4 信息维护与查询

* **信息修改**：可修改已发布信息的存放地点、联系人、联系电话（需记录修改日志），不可修改物品名称、类型、丢失 / 拾取时间等核心信息。

* **高级查询**：支持按物品名称、发布人、状态、时间范围、地点等多条件组合查询所有历史记录（包括普通用户看不到的驳回、无效记录）。

* **统计分析**：

* 查看实时统计数据：待审核信息数、已通过信息数、已认领数、未认领数。

* 查看周期统计（按日 / 周 / 月）：失物 / 招领信息发布量、认领成功率、各物品类型占比。

* 支持导出统计数据为 Excel 格式（可选功能）。

#### 4.2.5 站内通知管理

* 查看普通用户发送的咨询留言，支持回复留言，回复后用户将收到站内通知。

* 可向指定用户（如认领申请人）发送站内通知（如 “请于 3 个工作日内前往失物招领中心领取物品”）。

#### 4.2.6 退出登录

* 点击 “退出登录” 按钮，销毁会话令牌，返回登录页面。

### 4.3 系统管理员功能模块

#### 4.3.1 系统管理员登录

* **登录凭证**：使用超级管理员账号（预设账号）和密码登录，密码需定期修改（系统提示每 90 天修改一次）。

* **登录安全**：登录失败超过 5 次，账号锁定 1 小时；支持登录 IP 白名单设置（可选）。

#### 4.3.2 全局总览

* 查看系统运行核心数据：总用户数、失物信息总数、招领信息总数、已认领数、认领成功率、待审核信息数。

* 查看数据趋势图（按周 / 月）：失物 / 招领信息发布趋势、认领趋势。

* 查看系统运行状态：服务器负载、数据库连接数、接口调用成功率（可选监控功能）。

#### 4.3.3 账号与权限管理

* **普通用户管理**：查看所有学生 / 老师账号列表（支持按学号 / 工号、姓名搜索），仅可查看不可修改（账号信息由学校统一同步，系统管理员无权新增 / 修改普通用户）。

* **失物招领管理员管理**：

* 新增管理员：填写工号、姓名、联系电话，设置初始密码（默认身份证后六位），分配角色为 “失物招领管理员”。

* 禁用 / 启用管理员：对违规或离职的管理员账号进行禁用操作，禁用后无法登录系统；支持重新启用。

* 重置密码：可为失物招领管理员重置密码（重置后为初始密码，需强制修改）。

* **权限查看**：查看所有角色的权限矩阵，不可修改权限配置（权限配置为系统内置）。

#### 4.3.4 系统参数配置

* **基础参数配置**：

* 认领时效：设置招领信息的认领有效期（默认 30 天，可修改）。

* 发布频率限制：设置普通用户单日最多发布失物 / 招领信息数量（默认 5 条，可修改）。

* 照片规格：设置照片上传的格式、大小限制（默认 JPG/PNG，单张≤5MB）。

* **分类与地点管理**：

* 物品分类管理：新增、编辑、删除物品分类（支持多级分类，如 “电子设备” 下新增 “耳机”“平板”）。

* 校园地点管理：新增、编辑、删除校园地点（支持层级结构，如 “教学楼”→“A 栋”→“302 教室”）。

* **内容规范配置**：设置信息发布的内容禁忌词（如违规词汇），用户发布信息时系统自动检测，含禁忌词则提示 “内容不符合规范，请修改”。

#### 4.3.5 公告与内容管理

* **公告发布**：发布系统全局公告，填写公告标题、内容（支持富文本编辑，如插入图片、换行），设置生效时间、失效时间、优先级（高 / 中 / 低）。

* **公告管理**：查看所有公告列表，支持编辑、删除未失效的公告；对已失效的公告进行归档。

* **违规内容处理**：查看失物招领管理员上报的违规信息（如虚假信息、违规照片），支持直接删除信息、禁用发布者账号（需记录操作原因）。

#### 4.3.6 数据管理与维护

* **数据备份**：手动触发数据库备份（支持全量备份），设置自动备份计划（如每日凌晨 2 点自动备份），查看备份历史（支持下载备份文件）。

* **数据导出**：导出指定时间范围的失物 / 招领信息、用户账号信息、操作日志为 Excel 格式。

* **数据清理**：清理过期数据（如已归档超过 1 年的信息、超过 3 个月的操作日志），清理前需确认，清理后不可恢复。

* **投诉与反馈处理**：查看普通用户提交的投诉（如 “某招领信息为虚假信息”），支持标记处理状态（待处理 / 已处理），填写处理结果并回复用户。

#### 4.3.7 操作日志查看

* 查看系统所有关键操作日志，包括操作人、操作时间、操作模块、操作内容、IP 地址。

* 支持按操作人、操作时间、操作模块筛选日志，支持导出日志为 Excel 格式。

#### 4.3.8 退出登录

* 点击 “退出登录” 按钮，销毁会话令牌，返回登录页面。

五、数据库设计
-------

### 5.1 数据库设计原则

1. 严格遵循数据库第三范式（3NF），减少数据冗余，确保数据一致性。

2. 核心业务表（如物品信息表）适度反规范化（如冗余物品类型名称），提升查询效率。

3. 状态流转采用 “主表状态字段 + 状态历史表” 结合方式，主表存储当前状态，历史表记录状态变更轨迹，支持审计。

4. 敏感字段（如密码）采用加密存储（如 BCrypt 哈希算法），禁止明文存储。

5. 所有表均设计主键（PK），核心关联表设计外键（FK），确保数据完整性。

6. 大字段（如物品特征、公告内容）采用合适的字段类型（如 TEXT），避免占用过多存储。

7. 关键表设计索引（如物品信息表的类型、地点、时间字段），提升查询性能。

## 八、系统非功能需求

### 8.1 性能需求

#### 响应时间要求

- 普通页面（如登录、列表查询、详情查看）在正常网络环境下，服务器响应时间 ≤ 2 秒。
- 复杂查询（多条件筛选、统计分析）响应时间 ≤ 3 秒。
- 文件上传（图片）在单张 ≤ 5MB 的情况下，上传与处理时间 ≤ 5 秒。

#### 并发访问能力

- 系统应支持不少于 500 名用户同时在线访问（以普通用户查询、发布操作为主）。
- 在并发场景下（如公告发布后集中访问），系统不应出现崩溃、数据错乱或严重性能下降。

#### 数据库性能

- 高频查询字段（如物品类型、状态、时间、地点）必须建立索引。
- 列表查询默认分页，禁止一次性返回大量数据。
- 统计类查询优先使用预计算或缓存机制（如 Redis，选做）。

---

### 8.2 安全需求

#### 身份认证与授权

- 系统所有业务接口必须在后端进行身份认证，未登录用户禁止访问任何业务资源。
- 采用 Token（如 JWT）机制进行身份认证，Token 中包含用户 ID、角色信息，并设置有效期。
- 所有接口均进行角色权限校验，防止越权访问（如普通用户访问管理员接口）。

#### 密码与账号安全

- 用户密码必须采用不可逆加密算法（如 BCrypt）存储，禁止明文保存或传输。
- 密码修改需校验原密码，防止他人非法修改账号信息。
- 登录失败超过 5 次的账号将被临时锁定 1 小时，防止暴力破解。

#### 数据访问安全

- 普通用户仅能访问与自身相关的数据（如自己的发布记录、认领记录）。
- 用户联系方式等敏感信息仅对有权限的用户展示（管理员、失主 / 拾主）。
- 管理员操作涉及的数据修改必须记录操作日志，便于审计。

#### 输入校验与防攻击

- 所有用户输入数据需在前后端进行合法性校验，防止 SQL 注入、XSS 攻击。
- 富文本内容（公告、描述信息）需进行 HTML 标签白名单过滤。
- 文件上传需校验文件类型与大小，禁止上传可执行文件。

---

### 8.3 可靠性与可用性需求

#### 系统稳定性

- 系统应保证 7×24 小时可用，非维护期间不应无故中断服务。
- 发生异常时（如服务器错误），系统应返回友好提示页面，而非直接暴露错误信息。

#### 异常处理

- 对于常见异常（如网络异常、参数错误、权限不足），系统应有明确的错误提示。
- 后端接口统一返回规范化错误码和错误信息，便于前端处理。

#### 数据一致性

- 关键业务操作（如审核、状态修改、认领确认）需使用数据库事务，确保操作原子性。
- 防止重复提交（如重复发布、重复认领），通过前端按钮禁用 + 后端幂等校验实现。

---

### 8.4 可维护性与可扩展性需求

#### 代码结构

- 后端按模块拆分（用户模块、物品模块、审核模块、统计模块等），遵循高内聚、低耦合原则。
- 前端按页面和功能模块组织代码，避免逻辑混杂。

#### 配置可扩展

- 系统参数（如认领时效、发布频率、分类、地点）通过数据库配置，无需修改代码即可调整。
- 后期新增物品类型、地点层级、公告类型不影响现有功能。

#### 多端扩展能力

- 后端统一提供 RESTful API，PC Web 与后续微信小程序共用同一套接口。
- 前端与后端完全解耦，便于后续开发小程序或移动端应用。

---

### 8.5 可用性与易用性需求

#### 界面友好

- 页面布局清晰，功能入口明确，符合常见管理系统使用习惯。
- 操作按钮命名清晰，避免歧义（如“取消发布”与“删除”明确区分）。

#### 操作提示

- 关键操作（如提交、审核、删除）需有确认提示，防止误操作。
- 操作完成后给予明确反馈（成功 / 失败原因）。

#### 学习成本

- 普通用户无需培训即可完成基本操作（查询、发布、认领）。
- 管理员通过简单使用说明即可上手系统管理功能。
